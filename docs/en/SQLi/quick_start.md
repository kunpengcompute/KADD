This document provides a quick start guide for KADD. It provides a tool set and demo examples. By running the demo programs, you can quickly experience the SQL injection detection function. By using the tools, you can generate the DFA tables and train models. For details, see [User Guide](user_guide.md).

## Prerequisites

You have completed installation by following instructions in [Installation Guide](installation_guide.md).



## Demo Program Usage

KADD provides six demo programs to demonstrate how to use each engine.

### Running the Demo Programs

Before running the programs, you need to set the library search path and inject the model HMAC key (native `.krf`/`.kcn` models enforce HMAC-SHA256 authentication; without key injection, native models will be rejected from loading):

```bash
export LD_LIBRARY_PATH=/opt/KADD/SQLi/build/src:/opt/KADD/SQLi/util/onnxruntime-linux-aarch64-1.28.0/lib:$LD_LIBRARY_PATH
export KADD_MODEL_HMAC_KEY=74fab58d87dc235ee049b6faf21b44825dba1d9dc05bbc14aeded49cb211a1db
```

You can also directly source the environment file generated by `build.sh`, which is equivalent to the two commands above.

```bash
source /opt/KADD/SQLi/build/kadd_env.sh
```

![Note icon](../../public_sys-resources/icon-note.gif) **NOTE:**

- The key above is the **public development key** shipped with the repository. The models in the repository are signed with it. The key is intended only for build, testing, and feature experience, and is not confidential.
- When the key is not injected, native models will be rejected from loading and an error will be printed to stderr, after which the program falls back to ONNX (losing SVE acceleration). If `config.json` configures only native models, or if the program directly calls `kadd_rf_model_load()`/`kadd_cnn_model_load()`, loading will fail.
- For production deployment, you must re-sign the models with your own key (see the signing steps in *Model Training* below) and inject `KADD_MODEL_HMAC_KEY` through a KMS or an .env file with restricted permissions.

## Model Training

KADD uses the unified `model_train.py` training script and supports two model types:

| Model Type | Parameter Value | Input Feature | Output File | Description |
|---------|--------|---------|---------|------|
| Random Forest | `rf` | 28-dimensional feature vector | `.onnx` + `.krf` | Loads the native format first when SVE is available. |
| TextCNN | `dl_cnn` | 300-dimensional token sequence | `.onnx` + `.kcn` | Loads the native format first when SVE is available. |

### Prerequisites

#### 1. Installing Python Dependencies

```bash
pip install torch onnx onnxruntime pandas numpy scikit-learn skl2onnx
```

#### 2. Preparing the C Dynamic Libraries (DFA Tokenization + Feature Extraction)

```bash
cp /opt/KADD/SQLi/build/src/libkadd_dfa_engine.so /opt/KADD/SQLi/tools/model_train/
cp /opt/KADD/SQLi/build/src/libkadd_feature_engine.so /opt/KADD/SQLi/tools/model_train/
```

### Training a Random Forest Model (RF)

This is the most commonly used model type, suitable for low-latency scenarios.

1. Train the model using the default configuration and built-in data path.

    ```bash
    cd /opt/KADD/SQLi/tools/model_train
    python model_train.py --model-type rf
    ```

2. Train the model by specifying a custom data file.

    ```bash
    python model_train.py --model-type rf \
        --data /path/to/your/training_data.csv \
        --data-format raw
    ```

3. Train the model by specifying the model output path.

    ```bash
    python model_train.py --model-type rf \
        --model-output /opt/KADD/SQLi/assets/model/model_tokens_rf.onnx
    ```

4. When not using the default `config.json` path, train the model by specifying the DFA table paths.

    ```bash
    python model_train.py --model-type rf \
        --transition /opt/KADD/SQLi/assets/data/transition_table.bin \
        --output-table /opt/KADD/SQLi/assets/data/output_table.bin \
        --eod /opt/KADD/SQLi/assets/data/eod_table.bin
    ```

5. (Mandatory) Sign the newly generated native model.

    The `.krf` produced by training is **unsigned**, and the loader will reject it directly (fail-closed). You must use `rf_sign.py` for signing.

    ```bash
    export KADD_MODEL_HMAC_KEY=$(openssl rand -hex 32)   # Generate and securely store your own key in production environments.
    cd /opt/KADD/SQLi/tools/rf_sign
    python rf_sign.py --in-place /opt/KADD/SQLi/assets/model/model_tokens_rf.krf
    python rf_sign.py --verify /opt/KADD/SQLi/assets/model/model_tokens_rf.krf
    ```

    > **NOTE:**
    >
    > The signing key must match the runtime `KADD_MODEL_HMAC_KEY`. Re-signing is required if the key is changed. The ONNX format (`.onnx`) does not participate in HMAC authentication and does not require signing.

#### Expected Output

- `model_tokens_rf.krf`: native binary format (loaded first when SVE is available; **must be signed as described in step 5 before it can be loaded**)

### Training the TextCNN Model (DL_CNN)

This operation is suitable for scenarios that require higher detection accuracy.

1. Train the model with the default configuration.

    ```bash
    cd /opt/KADD/SQLi/tools/model_train
    python model_train.py --model-type dl_cnn
    ```

2. Specify the number of training epochs.

    ```bash
    python model_train.py --model-type dl_cnn --epochs 30
    ```

3. Specify the training data and model output.

    ```bash
    python model_train.py --model-type dl_cnn \
        --data /path/to/training_data.csv \
        --model-output /opt/KADD/SQLi/assets/model/model_tokens_dl_cnn.onnx
    ```

4. (Mandatory) Sign the newly generated native model.

    The `.kcn` produced by training is **unsigned**, and the loader rejects it directly (fail-closed).

    ```bash
    export KADD_MODEL_HMAC_KEY=$(openssl rand -hex 32)   # Must match that in the runtime environment.
    cd /opt/KADD/SQLi/tools/rf_sign
    python rf_sign.py --in-place /opt/KADD/SQLi/assets/model/model_tokens_dl_cnn.kcn
    python rf_sign.py --verify /opt/KADD/SQLi/assets/model/model_tokens_dl_cnn.kcn
    ```

#### Expected Output

- `model_tokens_dl_cnn.onnx`: model in ONNX format

### Data Format Description

The training script supports two data formats:

**1. Raw CSV format (recommended)**

Contains two columns, `Query` and `Label`. The script automatically invokes the C library for DFA tokenization and feature extraction.

```csv
Query,Label
"SELECT * FROM users WHERE id=1",0
"id=1' OR '1'='1",1
"admin'--",1
"hello world",0
```

**2. JSON format**

Contains pre-tokenized structured data, suitable for large-scale datasets that have already been tokenized.

```json
[
  {"tokens": [7, 11, 8, 12, 8], "label": 0},
  {"tokens": [3, 15, 22, 7, 11], "label": 1}
]
```

### Complete Parameter List

```bash
python model_train.py --help
```

| Parameter | Default Value | Description |
|------|--------|------|
| `--model-type` | `rf` | Model type: `rf` or `dl_cnn` |
| `--data` | Built-in CSV | Training data path |
| `--data-format` | `raw` | Data format: `raw` (original CSV) or `json` (pre-tokenization) |
| `--config` | `../../config.json` | Configuration file path |
| `--model-output` | Read from `config` | Model output path |
| `--transition` | Read from `config` | DFA transition table path |
| `--output-table` | Read from `config` | DFA output table path |
| `--eod` | Read from `config` | DFA EOD table path |
| `--dfa-so` | Auto-detected | DFA dynamic library path |
| `--feature-so` | Auto-detected | Feature dynamic library path |
| `--epochs` | `20` | Number of training epochs (DL models only) |

### Benchmark Test Dataset Generation

To create an independent test set for backend performance comparison, you can use the auxiliary scripts (no C dynamic library or PyTorch required):

1. Generate the RF benchmark test dataset. This dataset uses precomputed feature vectors.

    ```bash
    cd /opt/KADD/SQLi/tools/model_train
    python prepare_rf_benchmark.py
    ```

2. Generate the CNN benchmark test dataset. This dataset requires the DFA library for tokenization.

    ```bash
    python prepare_cnn_benchmark.py
    ```
